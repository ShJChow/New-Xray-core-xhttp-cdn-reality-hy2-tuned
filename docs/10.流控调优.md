> **v4.2.0 变更（重要）**：**内核层调优回归安装流程，默认自动执行**。
> v2.0.0 曾把内核 / 句柄 / systemd 调优从安装流程拆出（需手动 `xh tuning on`），
> 原因是怕 OpenVZ / LXC 只读 sysctl 阻断安装。调优逻辑自 v2.0.0 起已全部
> **best-effort**（逐项试写、失败只告警），因此 v4.2.0 起安装完成时自动执行
> `xh tuning on`。`FEATURE_AUTO_TUNING=false` 可跳过，`xh tuning off` 一键回滚。
>
> 同时移除的还有：Nginx 的吞吐旋钮、客户端 `xmux` 的自定义值（用回上游的
> `16-32` / `1800-3000`）。

> **v3.0.0 变更（重要）**：**Xray 应用层参数回归安装期**。
> `policy.bufferSize` 与 `sockopt` 是 Xray **进程内**的分配与 socket 选项，sysctl 调不到，
> 只能在 config.json 里写。v3.0.0 起安装脚本会把这两项渲染进 `xray-config.json`；
> v4.2.0 起内核层调优也在安装时自动执行。
>
> 分层的边界：**内核层 → `xh tuning on`；Xray 应用层 → 安装脚本**。两层互不
> 冲突，见下方 §0。

## 0. 分层：安装脚本写的 vs `xh tuning on` 写的

| 层级 | 谁写 | 何时生效 | 回滚 |
|---|---|---|---|
| `policy.bufferSize`（按内存分档 512/256/64 KB） | 安装脚本渲染进 config.json | 安装后立即 | 重装 / 手动改 config |
| Reality 入站 `sockopt`（TFO / tcpcongestion / keepalive / tcpUserTimeout） | 安装脚本渲染进 config.json | 安装后立即 | 重装 / 手动改 config |
| 内核 sysctl（BBR / 缓冲 / TFO / 句柄…） | `xh tuning on` | 手动执行后 | `xh tuning off` |

为什么 bufferSize 和 sockopt 必须在安装期写，不能交给 `xh tuning on`：

- **bufferSize**：Xray 进程启动时按配置分配内部缓存。ARM64 上默认只有 **4 KB**
  （x86 是 512 KB），同样配置 ARM 机器吞吐被压死——这不是内核参数，sysctl 改不了。
- **sockopt**：Xray 建 socket 时应用这些选项（TFO、拥塞算法、TCP_USER_TIMEOUT）。
  同样在 Xray 进程内，与内核 sysctl 是两回事。

`tcpcongestion` 仅在探测到 BBR 时写入（否则 `xray -test` 失败，见 §5）。
服务端 xhttpSettings 不注入流控字段——源码查证其默认值已合理，客户端侧的
`scMinPostsIntervalMs: 30` 在节点 URI 里已有。

# XHTTP + CDN 搭建指南 (十)：流控调优

本文描述 `xh tuning on` 会应用的内核与句柄参数。实现在 `src/06-tuning-lib.sh`，该文件被内联进管理命令 `xh`，**不在安装流程里执行**；也可按本文手动执行。

> **设计原则**
>
> 1. **只写自己的文件**：内核参数写 `/etc/sysctl.d/99-xray-xhttp.conf`，句柄写 `/etc/security/limits.d/99-xray-xhttp.conf`，服务限额写 systemd drop-in。**不修改**你原有的 `/etc/sysctl.conf`，也**不修改**官方 Xray-install 维护的 unit 文件（避免内核更新后被覆盖）。
> 2. **全部 best-effort**：逐项试写，失败只告警不中断。OpenVZ / LXC 等只读 sysctl 环境会自动跳过。
> 3. **可整体回滚**：`xh tuning off`。

## 1. 内核参数

`xh tuning on` 会先做能力探测：

```bash
sysctl -n net.ipv4.tcp_available_congestion_control   # 是否含 bbr
modprobe tcp_bbr                                      # 不含时尝试加载模块后复测
```

**只有探测通过才启用 BBR**；否则保持系统默认拥塞算法，其余参数照常应用。

**部分参数按机型分档**（内存 ≥16 GB / ≥4 GB / <4 GB 三档），完整分档表见 [12.机型调优-OracleARM.md](./12.机型调优-OracleARM.md)。下表 `档位值` 列的三个数依次对应 large / medium / small。

| 参数 | 值 | 作用 |
|---|---|---|
| `net.core.default_qdisc` | `fq` | BBR 的配套队列调度，缺它 BBR 收益大打折扣 |
| `net.ipv4.tcp_congestion_control` | `bbr` | 基于带宽时延积的拥塞控制，跨境高丢包链路收益最大 |
| `net.core.rmem_max` / `wmem_max` | 档位值 64/32/16 MB | 单连接最大收发缓冲，决定高 BDP 链路的吞吐上限 |
| `net.core.rmem_default` / `wmem_default` | `1048576` | 默认缓冲 |
| `net.ipv4.tcp_rmem` | `4096 262144 <32/16/8 MB>` | TCP 接收缓冲自动调节区间。中间值是**初始**默认值，autotuning 会在 min~max 间增长；调大它影响的是连接建立初期与短流 |
| `net.ipv4.tcp_wmem` | `4096 262144 <32/16/8 MB>` | TCP 发送缓冲自动调节区间，同上 |
| `net.ipv4.tcp_adv_win_scale` | `-2` | 接收缓冲中留给协议开销的比例，负值按 1/2^\|n\| 计。新内核语义几经调整且 `tcp_moderate_rcvbuf` 已覆盖多数场景，**不断言收益**；内核不支持时会被记入 SKIPPED |
| `net.ipv4.tcp_mem` | 物理内存页数的 6%/8%/12% | TCP 全局内存页阈值，随机器内存伸缩 |
| `net.core.optmem_max` | `65536` | 每 socket 辅助缓冲 |
| `net.ipv4.udp_rmem_min` / `udp_wmem_min` | `16384` | QUIC / HTTP3（`add-quic.sh` 与 Hysteria2）用，高于默认 8192 |
| `net.core.netdev_max_backlog` | 档位值 65536/32768/16384 | 网卡收包队列，高 PPS 下防丢包 |
| `net.core.netdev_budget` | 中/大内存档 6000，小内存档不写 | NAPI 每轮 poll 可处理的包数上限。默认 300 在 CDN 回源 + XHTTP 长连接的大量小包场景下 softirq 收不完（`/proc/net/softnet_stat` 的 `time_squeeze` 非零即此信号）。放大是"在 2000μs 窗口内多收包"而非延长窗口，不增加软中断时长 |
| `net.core.somaxconn` | `65535` | accept 队列上限（Nginx / Xray 高并发） |
| `net.ipv4.tcp_max_syn_backlog` | 同 netdev_max_backlog | 半连接队列 |
| `net.netfilter.nf_conntrack_max` | 档位值 1048576/262144/不调整 | 仅在 conntrack 模块已加载时写入 |
| `net.ipv4.tcp_max_tw_buckets` | `65536` | TIME_WAIT 上限 |
| `net.ipv4.ip_local_port_range` | `1024 65535` | 本地端口范围（出站并发） |
| `net.ipv4.tcp_fastopen` | `3` | TFO 客户端 + 服务端同时开启，省一个 RTT |
| `net.ipv4.tcp_mtu_probing` | `1` | PMTU 黑洞探测，避免中间设备丢 ICMP 导致大包卡死 |
| `net.ipv4.tcp_slow_start_after_idle` | `0` | 空闲后不回到慢启动，XHTTP 长连接的关键项 |
| `net.ipv4.tcp_notsent_lowat` | `16384` | 套接字里允许积压的未发送字节数。调小 = Xray 更早被唤醒补数据，本地排队更少，降低队头阻塞与写入延迟。这是**延迟**收益不是吞吐收益——拥塞窗口由 BBR 与 rmem/wmem 决定，与本项无关 |
| `net.ipv4.tcp_syncookies` | `1` | SYN 洪泛保护 |
| `net.ipv4.tcp_tw_reuse` | `1` | 复用 TIME_WAIT（仅出站方向安全） |
| `net.ipv4.tcp_retries2` | `8` | 死连接在内核层约 1 分钟内被关闭（默认 15 ≈ 15 分钟）。代理机上对端死亡后连接表槽位与 fd 被僵尸连接占住，收得越快、给正常连接腾的资源越多；瞬时抖动可能更早报错，但 Xray 自动重连能更快接管 |
| `net.ipv4.tcp_syn_retries` | `4` | 出站 SYN 约 30s 放弃（默认 6 ≈ 3 分钟）。发往回落站/上游的连接对端若不可达，不必为已死的对端白等 |
| `net.ipv4.tcp_rfc1337` | `1` | TIME_WAIT 暗杀保护。默认 0 时对端在 TIME_WAIT 期发来的 RST 会提前终结连接、破坏 2MSL 语义；1 忽略该 RST，零成本的防御性设置 |
| `net.ipv4.tcp_fin_timeout` | `15` | 缩短 FIN_WAIT2 |
| `net.ipv4.tcp_keepalive_time` / `intvl` / `probes` | `300` / `30` / `5` | 300s 先于 CDN/NAT 常见的 900s 空闲回收探活，更快回收僵死连接 |
| `vm.overcommit_memory` | `0` | 启发式 overcommit。不设 `1`（总是允许）——Xray 不是 Redis，不需 fork 快照的 overcommit 语义，`1` 在极端情况下可能 OOM |
| `fs.file-max` / `fs.nr_open` | `1048576` | 系统级句柄上限 |

**未采用的项及原因**：

- `tcpMptcp` / MPTCP：需两端同时支持，经 CDN 中转无意义，默认关闭。
- 更换内核（XanMod / BBRv3 / BBRplus）：需重启换内核，与 VPS 提供商强耦合、回滚成本高，收益主要已由 BBR+fq 覆盖。

## 4. flow / Vision：哪些节点能用，哪些用不了

### 只有节点 1 能用 Vision

`xtls-rprx-vision` 要求 **TCP + TLS/REALITY 的 raw 传输**。本项目里只有节点 1（`Vless-reality-vision-*`）满足，它也是唯一能触发 **Splice**（内核直接转发 TCP，不经 Xray 内存）的节点。

节点 2–5 全部是 **XHTTP 传输，按 Xray 的设计就不能带 flow**，服务端 XHTTP 入站的 client 也不写 `flow`。这不是配置漏了，是协议限制——给 XHTTP 节点加 Vision 只会让连接失败。

**所以"所有节点都开 Vision"做不到。** 追求单节点速度请优先用节点 1。

### 默认值与 `-udp443`

节点 1 的 flow 默认写 `xtls-rprx-vision`。想要不拦截 UDP 443（让强制走 QUIC 的程序可用），部署时加环境变量：

```bash
VISION_UDP443=1 bash ~/install-xpadding.sh
```

**为什么不默认开**：部分客户端不认识 `xtls-rprx-vision-udp443`，会把 flow 直接置空。而服务端 account 的 flow 是 `xtls-rprx-vision` 时，客户端空 flow 会被**直接拒绝**：

```
account ... is rejected since the client flow is empty.
Note that the pure TLS proxy has certain TLS in TLS characters.
```

（见 Xray `proxy/vless/inbound/inbound.go` 的 `case "":` 分支）——表现是节点完全连不上，而不是变慢。

### 服务端永远写 `xtls-rprx-vision`

即使客户端用了 `-udp443`，**服务端入站也只能写 `xtls-rprx-vision`**：

- `proxy/vless/vless.go` 中 `XRV = "xtls-rprx-vision"` 是唯一常量。
- 客户端的 `-udp443` 只是本地开关（`outbound.go` 中 `case XRV + "-udp443"` 置 `allowUDP443` 后 fallthrough），**上线时发送的仍是 `xtls-rprx-vision`**。

**Mihomo 例外**：mihomo 会把 `flow` 截断到前 16 字符再比对，写 `-udp443` 不报错但没有任何效果，因此 Mihomo 模板固定为 `xtls-rprx-vision`。

## 5. Xray `sockopt`

> **v3.0.0 起**：安装脚本会把 sockopt 注入 **Reality 入站（443）** 的
> `streamSettings`。XHTTP 入站（`127.0.0.1:8001`）是 loopback，不经过 TCP 栈，
> TFO / 拥塞算法对它无效，故不注入。

```json
"sockopt": {
    "tcpFastOpen": true,
    "tcpcongestion": "bbr",
    "tcpKeepAliveIdle": 100,
    "tcpKeepAliveInterval": 30,
    "tcpUserTimeout": 10000
}
```

注意事项：

- 字段名是 **`tcpcongestion`（全小写 c）**，不是 `tcpCongestion`（见官方 sockopt 文档）。
- **`tcpcongestion` 只在探测到 BBR 时写入**。内核不支持时写入会导致 `xray -test` 失败、服务起不来；无 BBR 时仍写 TFO / keepalive / tcpUserTimeout。
- `tcpNoDelay` 已在新版 Xray 中废弃移除（Go 默认即开启 TCP_NODELAY），不要再写。

### 客户端手动加 sockopt

VLESS 分享链接（`vless://`）**无法携带 sockopt**。若使用 V2rayN 的 JSON 配置，可在对应 outbound 的 `streamSettings` 里手动补：

```json
"streamSettings": {
  "network": "xhttp",
  "sockopt": {
    "tcpFastOpen": true,
    "tcpKeepAliveIdle": 100
  }
}
```

Windows 客户端不要写 `tcpcongestion`（Linux only）。

## 6. Nginx

```nginx
worker_rlimit_nofile 1048576;

events {
    worker_connections 65535;
    multi_accept on;
    use epoll;
}

http {
    keepalive_timeout   75s;
    keepalive_requests  10000;
    client_body_buffer_size 128k;
    ...
    location /你的XHTTP路径 {
        grpc_pass 127.0.0.1:8001;
        grpc_socket_keepalive on;
        grpc_read_timeout     1h;
        grpc_send_timeout     1h;
        grpc_connect_timeout  15s;
    }
}
```

关于 `grpc_read_timeout` / `grpc_send_timeout`：Nginx 对上游的读写超时默认 60s，而 XHTTP 的下行是长连接。**机制上**，空闲超过该超时后 Nginx 会关闭到 Xray（`127.0.0.1:8001`）的这条上游连接，客户端需要重新发起；放大到 `1h` 可以减少这类重连。

> 上游 `my-xhttp-cdn-config` 未设置这两项也能正常工作，本项目**未对该改动做定量实测**，请按"合理改进"而非"已验证的故障修复"来理解。

## 7. 客户端 `xmux`

xpadding 版脚本生成的节点链接已自动带上：

```json
"xmux": {
  "maxConcurrency": "16-32",
  "cMaxReuseTimes": 0,
  "hMaxReusableSecs": "1800-3000",
  "hKeepAlivePeriod": 0
}
```

> **v1.2.3 调大**：`maxConcurrency` `16-32` → `16-32`，`hMaxReusableSecs` `1800-3000` → `1800-3000`。
> 前者提高单连接上的并发子流数，后者延长 HTTP 连接可复用时长、减少重建握手。
>
> **`hKeepAlivePeriod: 0` 不是"关闭"**（此前文档未说明，易误读）。查 Xray 源码
> `transport/internet/splithttp/dialer.go:182-186`：h3 路径下 `0` 表示**采用 Xray 的
> QUIC 默认 keepalive**（`net.QuicgoH3KeepAlivePeriod`），h2 路径下取
> `net.ChromeH2KeepAlivePeriod`；只有**负值**才是禁用。所以这里保持 `0`——
> 盲目改成正值反而会覆盖掉 quic-go/Chrome 的经验默认值。
>
> `cMaxReuseTimes: 0` 同理表示**不限制**复用次数，已是最宽松，无需再调。

`xmux` 是**客户端侧**字段，服务端入站写它没有效果。服务端也**不建议**调大 `scMaxEachPostBytes`——该值在服务端是**上限**语义，调过大反而可能拖累客户端。

Mihomo 客户端的 TCP Fast Open 字段（`tfo`）**未纳入**本项目生成的模板：未核实其在 XHTTP 传输下的实际行为，宁可不写也不写错。需要的话可自行在 `proxies` 条目中添加并自测。

> **勘误**：早期文档写过"未核实 mihomo 对 XHTTP-over-H3 的支持"，该结论是错的。mihomo `transport/xhttp/client.go:159` 与 Xray 一样在 `len(alpn)==1 && alpn[0]=="h3"` 时走 HTTP/3，因此 Mihomo 配置里也包含 UDP 节点（v1.2.7 起为经 CDN 的那一条；直连那条已默认停用）。

### 服务端 sockopt 的实际作用面

需要说明的是，XHTTP 入站监听在 `127.0.0.1:8001`（由 Nginx 反代进来），它的 `sockopt` 只影响本机回环连接，拥塞算法与 TFO 在这条链路上**基本不产生收益**。真正起作用的是 **443 的 Reality 入站**与 **freedom 出站**这两处。写在 XHTTP 入站上是为了配置一致、无副作用，不要高估它。

## 8. UDP / HTTP3 节点

本项目唯一的 UDP 节点是 **节点 4 `Vless-xhttp-tls-UDP-cdn`**（经 CDN，`alpn=h3`）。

它由 Cloudflare 边缘终结 HTTP/3，回源到你的机器仍然是 TCP，因此**服务端零改动**，
不需要 Nginx 监听 `UDP 443 quic`，也不需要在防火墙放行 UDP 443。前提只有两条：

1. 你的 Cloudflare 区域已开启 HTTP/3（默认开启）；
2. 你的**客户端网络**允许 UDP 443 出站。

> **v2.0.0 移除了直连 VPS 的 h3 节点**（原 `Vless-xhttp-tls-UDP-direct`）。
> 该节点在 Shadowrocket 下实测不通，且它是配置里唯一需要 `listen 443 quic` 的部分——
> `http3` 依赖支持 QUIC 的 TLS 库（标准 OpenSSL 未必满足），曾导致部分环境 nginx 启动失败。
> 一并移除后，`nginx.conf` 不再有任何有 SSL 库依赖的指令。

**节点 4 不通时**先跑 `xh diag`。它不经过本项目的服务端配置，所以挂掉基本只剩一个
共同因子：客户端侧网络封锁了 UDP 443（QUIC）。此时服务端无解，改用节点 1 / 2 / 3 / 5
（全部走 TCP）。

另外注意 **TUN 模式下的自环**：开启 TUN 后若节点自身流量未豁免，Mihomo 发往节点服务器的
QUIC 包会被自家 TUN 再次捕获形成环路（TCP 因 dialer 绑定物理接口的保护更完整而不受影响）。
生成的 `client-config-mihomo-full.yaml` 已内置 `tun.route-exclude-address`、
首条 `DIRECT` 规则与 `sniffer.skip-dst-address` 三道防线。

## 9. 查看与回滚

```bash
xh status          # 当前 qdisc / 拥塞算法 / rmem_max / tcp_fastopen / xray 进程 nofile
xh tuning show     # 打印本项目写入的 sysctl.d 与 limits.d 内容
xh tuning off      # 删除本项目写入的全部调优文件并重载
```

调优前的完整快照保存在 `/etc/xhttp-cdn/sysctl-before.txt`。

`xh tuning off` 会移除持久化配置，但**已经生效的运行时内核参数需重启系统才能完全恢复默认值**。

安装完成时自动执行调优（v4.2.0 起），跳过用 `FEATURE_AUTO_TUNING=false`，回滚用 `xh tuning off`。
