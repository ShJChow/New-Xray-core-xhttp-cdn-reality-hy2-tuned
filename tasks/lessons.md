# Lessons

## 2026-07-26 · 生成 xray-xhttp

### L1 · `set -e` 下的调优模块必须 best-effort

**失败机制**：构建器给产物加了 `set -e`。`sysctl -w`、`modprobe tcp_bbr`、写 `limits.d` 在 OpenVZ / LXC / Alpine 上都可能失败，一旦失败会在 Xray 已安装但配置尚未生成的中间态整体中断，留下半成品系统。

**规则**：任何"锦上添花"的系统级写操作，一律先能力探测再逐项试写，失败只 `warn`，绝不让它成为 AND-OR 链的最后一条命令。

### L2 · 未加引号的 heredoc 渲染模板时，`$` 属于 shell 不属于目标配置

**失败机制**：`cat > /etc/nginx/nginx.conf << NGINXEOF` 会展开模板里所有 `$`。新增 `$request_time`、`$binary_remote_addr` 这类 nginx 变量若不写成 `\$`，渲染后直接变成空串，且**语法仍然合法**，故障只在运行时暴露。

**规则**：往这类模板加行前，先确认 heredoc 是否加引号；未加引号则所有目标语言的变量必须转义，改完立刻 `grep '\$' 模板 | grep -v '\\\$'` 复查。

### L3 · 配置字段名不凭记忆写

**失败机制**：`tcpcongestion` 与 `tcpCongestion` 大小写不同；`tcpNoDelay` 已被 Xray 移除；`scMaxEachPostBytes` 在服务端是上限而非目标值。凭印象写出的配置可能让 `xray -test` 直接失败，或产生反向优化。

**规则**：写第三方配置字段前查官方文档（`xtls.github.io/config/transports/sockopt.html` 等），并用离线渲染 + 解析器（`python -m json.tool`）在本地先验证一遍结构。

### L4 · 单位换算不能假定平台常量（页大小）

**失败机制**：`net.ipv4.tcp_mem` 的单位是"页"，而 `MemTotal` 是 kB。写 `$2/4` 等于硬编码 4 KB 页。RHEL 系的 aarch64 内核（Oracle Linux / UEK）常用 **64 KB 页**，页数会偏大 16 倍——24 GB 机器算出的 `tcp_mem` 上限超过物理内存，TCP 永远不进入内存压力状态，只会一直分配。方向恰好是最坏的那一侧。

**规则**：凡涉及"页/块/扇区"单位的换算，一律用 `getconf PAGESIZE` 之类的运行时查询，不写常量；并补一条**量纲断言**（如"`tcp_mem` 上限必须小于物理内存"）而不只是打印数值——这类 bug 靠肉眼看数字发现不了。

### L5 · 测试里手抄的函数副本 = 测不到漂移

**失败机制**：渲染测试里把 `render_policy_json` / `render_sockopt_kv` 手抄了一份。当时与源码一致，但源码一改，测试仍然测的是旧副本，还照样"全绿"。

**规则**：测试要执行**产物里的真实代码**（用 `awk` 从 `dist/*.sh` 抽取函数定义再 `source`），而不是复制一份等价实现。

### L7 · 有环境依赖的高风险改动，即使按要求恢复也要留逃生舱

**背景**：v1.1.0 加的 nginx `443 quic` 监听导致启动失败（用户反馈），v1.1.3 按要求移除。随后用户又要求"回滚到 1.2 版本的节点"，即明知风险也要把它恢复。

**规则**：当用户明确要恢复一个曾经出问题、且本机无法验证的改动时，不要原样回滚了事——加一个默认开启但可一键关闭的功能开关（`FEATURE_H3_DIRECT=false`），让下次同样的失败不需要再等一轮"报告报错 → 改代码 → 发版"，用户自己就能排除。开关要同时覆盖配置生成端（nginx 模板）和产物端（对应的节点链接），避免关闭后留下连不上的死节点。

### L9 · "未核实"的结论会被后续当成事实沿用，要主动回头查证

**失败机制**：为了不写错，我在 docs 里写了"未核实 mihomo 对 XHTTP-over-H3 的支持"，于是 Mihomo 配置一直不含 UDP 节点。三个版本之后才去看源码——`transport/xhttp/client.go:159` 明确支持（`len(alpn)==1 && alpn[0]=="h3"`）。谨慎的措辞变成了一个**长期少交付的功能**，并且写进了公开文档。

**规则**：`未核实` 只是临时状态，不是结论。凡是写下这四个字的地方都要留一条待办；下一次触碰相关代码时优先查证。查证成本通常只有一次 `curl` 源码 + 一次 grep，远低于功能长期缺失的代价。纠正时要在文档里显式标注"勘误"，而不是悄悄改掉。

### L10 · 删节点/改命名前，先问"谁在按名字找它"

**失败机制**：v1.1.1 已经因为改节点名让三个扩展脚本全挂过一次。本次删除 h2 的 CDN 节点时，`NODE_RE_CDN_BOTH` 找的正是那条——不处理就是同一个 bug 的第二次复发。

**规则**：删除或重命名任何"被其它组件按字符串定位"的产物前，先 `grep` 出所有定位点，并把回归测试**覆盖到全部历史格式**（本项目是 v1.0.0 中文名 / v1.1.4 八节点 / v1.2.0 四节点三代并存）。测试要断言"命中了哪一条"，而不只是"有没有命中"——两条候选并存时优先级错了同样是 bug。

### L8 · 交付时如实区分"已构建"与"已验证"

**规则**：本机无法运行的部分（VPS 上的证书签发、服务启动、链路连通性）必须在报告里单独列为未验证项，不能让"构建成功、语法检查通过"读起来像"功能可用"。

### L11 · 服务端 `server_name` 与客户端 `sni` 必须成对核对，不能各自演进

**失败机制**：`extensions/common-nodes/02` 把 QUIC 监听与 `location` 插进 **Reality 域名**的 server 块，`03` 生成的节点却发 `sni=CDN_DOMAIN`。两个文件各自都"看着对"，但 TLS 握手按 SNI 选 server 块，请求落到回落网站上，节点从上线起就没通过。更糟的是：因为从未被命中，那条 `location` 缺少 `grpc_read_timeout` 也一直没暴露——修好 SNI 的同时会立刻冒出"每 60 秒断一次"的第二个 bug。

**规则**：改动任何 `sni` / `host` / `servername` 之前，先 `grep` 出服务端对应的 `server_name`，确认二者字面相等；改完把"监听 + location + server_name + 客户端 sni"作为**一个整体**断言（本次的渲染测试正是这样写的）。另外，**让一段死代码复活时，要按新代码审一遍它**——它从未运行过，等于从未被验证过。

### L12 · 上游同源项目是最廉价的反证来源

**背景**：本项目以 `Yulinanami/my-xhttp-cdn-config` 为基座。两次 `curl` 拉到上游 `extensions/quic/02-server-config.sh`，就确认了上游是插进 **CDN** 块并复用该块已有 location——立刻反证我们插进 Reality 块是错配，而不是"另一种可行设计"。

**规则**：改动继承自上游的模块前，先花一次 `curl` 看上游当前怎么写。注意上游默认分支可能是 `master` 而非 `main`（本次 `main` 全部 404，用 `contents` API 的 `download_url` 才拿到正确分支）。

### L13 · `set -e` 下裸调用会启动失败的命令 = 永远拿不到根因

**失败机制**：`src/10-service-check.sh` 里 `service_restart nginx` 是裸调用。`systemctl restart` 返回非零 → `set -e` 立刻中断 → 下一行的 `service_is_active nginx || error "Nginx 启动失败"` **永远执行不到**。用户屏幕上只有 systemd 一句 "See systemctl status nginx.service"，我们自己写的判定与提示一句都没输出。这个 bug 在 v1.1.0 引入 quic 时就存在，三个版本里每次 nginx 启动失败都在浪费一整轮往返。

**规则**：凡是"可能失败且失败原因需要现场证据"的命令，一律 `if ! cmd; then dump_diagnostics; fi`，不要裸调用。诊断函数要在**第一次**失败时就把 journalctl / 端口占用 / LSM 状态一次性打全——远程排障的成本是一轮对话，本地多打 20 行日志的成本是零。

### L14 · `nginx -t` 通过 ≠ nginx 能启动，两者验证的是不同东西

**失败机制**：`nginx -t` 只解析配置、不 bind 端口、不初始化 QUIC/TLS 运行时。所以 `listen 443 quic` 的失败模式恰好落在 `-t` 的盲区里：语法检查全绿，`systemctl restart` 直接挂。我们的自检把 `nginx -t` 当成了"配置没问题"的证据。

**规则**：把"能否启动"当作独立于"语法是否合法"的验证项。对这类只在运行期暴露的高风险配置段，用 BEGIN/END 标记框起来，失败时自动删段重试——这既是自愈，也是一次干净的二分：删掉能起来就是它，删掉还起不来就不是它。

### L15 · "两条节点都不通"要先找它们的**唯一共同点**，而不是各自排查

**失败机制**：v1.2.0 时我从"两条 UDP 节点同时失败"推出"共同因子在客户端"，结论方向对，但停在了太粗的粒度上，写进文档后就成了"服务端改不了，改用 TCP 节点"。这次用户补上"TUN 模式"这个条件，共同点才收敛到可操作的层：节点 3 的 server 是域名、节点 4 是裸 IP，两者唯一的共同点就是 **QUIC**；而 TCP 的节点 1/2 正常，说明不是网络封锁 UDP，是 TUN 自环——客户端配置能修。

**规则**：多个组件同时失败时，先把它们的差异**逐项列出**（协议/地址形态/是否过 CDN/是否碰服务端），剩下的唯一交集才是根因所在的层。列不出交集就说明还缺一个条件，去问，而不是下"改不了"的结论。

### L16 · 默认值为 `0` 的第三方字段，先查它是"关闭"还是"用默认"

**失败机制**：我们的 `xmux` 一直写 `hKeepAlivePeriod: 0`，文档也照抄没解释。用户要求"调优拉大"时，直觉是把 0 改成正值。查 `transport/internet/splithttp/dialer.go:182-186` 才发现 h3 路径下 `0` = **采用 quic-go/http3 的经验默认**，只有负值才是禁用——把它改成拍脑袋的正值等于**覆盖掉更好的默认**，方向恰好相反。`cMaxReuseTimes: 0` 同样是"不限制"而非"不复用"。

**规则**：调参前先确认 `0` 的语义（关闭 / 无限 / 采用默认），三者的正确动作完全相反。这类语义只能从源码或官方文档读，读不到就不动它，并在文档里写清楚为什么不动。

## 2026-07-28 · v1.2.7 节点方案回归

### L17 · 「回退到版本 X」是症状描述，不是根因诊断——先 diff 再动手

**失败机制**：用户说「回退到版本 1.2.5，direct 的两个节点不通」，读起来像 v1.2.6 引入了回归。
若直接 `git revert`，会连带删掉 v1.2.6 的 `tools/perf-audit.sh`（383 行全新文件）、`xh conflict`
和三项 nginx 调优——**而且修不好问题**：`git diff v1.2.5 v1.2.6` 只动了 resolver 协议族、
`access_log off`、`listen backlog=65535`，全部不在 H3/QUIC 路径上。直连 h3 的问题从 v1.2.0
时代就存在。

**规则**：收到「回退到 X」时，先 `git diff X HEAD -- <相关路径>` 看**具体 hunk**（不是 `--stat`），
确认 X→HEAD 是否真的是回归源。不是的话，把这个发现当成结论告诉用户，并把「以 X 为方案基线、
保留其余工作」写成显式假设，而不是照字面执行一次破坏性回滚。

### L18 · 移植上游代码时，`${VAR:+…}` guard 不能"顺手规范化"

**失败机制**：上游的上下行分离节点把 padding/xmux 包在 `${XPAD_FIELDS_ENC:+…}` 里，却把
`downloadSettings` 留在 guard **外面**，所以 `extra=` 恒定输出。本项目的风格是不带 guard 的
`${EXTRA_4_PARAM}`，而它在 `normal` profile（`FEATURE_XPADDING=false`）下整体为空。若把上游
的写法"统一"成本项目风格，normal 版会**整体丢掉 `downloadSettings`**——节点退化成普通
CDN/Reality 节点，**能连通、看着完全正常**，是最难发现的一类静默错配。

**规则**：移植含条件展开的模板行时，逐字保留原 guard 结构；只做变量名映射
（如上游 `CDN_ECH_QUERY_ENC` → 本项目 `CDN_ECH_URI_PARAM`），不做风格统一。
并且**每个 profile 都要单独渲染断言**——只测 xpadding 版会让 normal 版的退化完全逃逸。

### L19 · 同一节点的 URI 版与 mihomo 版是两处独立代码，改一处必然漏另一处

**失败机制**：把 h3 的 `maxConcurrency` 提到 64-128 时，改了 `XMUX_H3_ENC`（URI 用），
漏了 `Vless-xhttp-tls-UDP-direct` 的 mihomo heredoc 块——两者都在 `11-client-config.sh` 里，
相隔 70 行。靠肉眼 review 没发现，是 V2 的**交叉断言**（"h3 节点在 URI 和 YAML 里都必须是
64-128"）抓出来的。

**规则**：任何节点参数改动，验证脚本要对 URI 与 mihomo YAML **同时**断言同一个值，
而不是分别检查各自"看着对不对"。

### L20 · 「整个模块废弃」之前先数清楚它产出几个东西

**失败机制**：我向用户建议「`add-quic.sh` 的唯一产物就是那条不通的 h3 节点，整个扩展废弃」，
用户据此选了废弃。读 `extensions/common-nodes/03-client-config.sh:5-6` 才发现它同时产出
`Hysteria2-direct`——独立协议，与 h3 完全无关。按原建议执行会误删一个能用的功能。

**规则**：给出「整体删除」这类不可逆建议前，必须先读完该模块的产物清单（grep 它的
`NODE_*_NAME` / 输出块），不能从模块名或文档标题推断。发现自己给错了前提要立刻更正并重新问，
不要因为用户已经答过就将错就错。

## 2026-07-28 · Go/Rust 重写评估

### L21 · 评估「要不要换语言」之前，先确认目标代码在不在数据路径上

**失败机制**：用户问「用 Go 或 Rust 重写本项目可行吗」，我写了一份完整的可行性评估——
语言构成、分发模型约束、按 `lessons.md` 分类反事实收益、Go vs Rust 选型、混合方案。
逐条都成立，但答的是错的问题：追问动机后是「晚高峰 Reality 卡顿丢包」。而本仓库
**安装完成即退出**，链路上跑的是 Xray-core（本来就是 Go）、nginx、内核 TCP 栈，
本项目对数据面的全部贡献是它**渲染出去的那些配置数值**（`${XRAY_SOCKOPT_JSON}`、
sysctl、客户端 xmux 分层、nginx `backlog` / `access_log off` 等），安装完这些值就固化在
Xray/nginx/内核里，与渲染它们的脚本用什么语言写无关。
因此重写**语言**对吞吐/延迟的影响**精确为零**，不是「收益小」。我在首轮正文里写过这句判断，
但埋在选型段落里当次要论据，没有顶到结论位置。

**规则**：收到重写/换语言/换框架类提问，先问「要解决的具体痛点是什么」，再动笔。
评估的第一段必须是**目标代码的运行期职责边界**（何时启动、何时退出、哪些字节经过它），
而不是语言特性对比——边界一画出来，一整类动机会当场失效，省掉整篇评估。

### L22 · 随时间周期变化的故障，根因必然不在代码里

**失败机制**：「晚高峰卡顿」+「高性能机器」这两个条件本身就是完备的排除证据——
代码不看时钟，纯配置渲染不可能 20:00 比 04:00 差；CPU 瓶颈应当随机器变强而缓解，
而现象与机器性能反向。但这两条要主动说出来才起作用，用户给的是体感描述。

**规则**：拿到故障描述先提取**时间维度与资源维度**两个条件，各自能排除掉什么写清楚，
再谈假说。同机器/同时刻的 CDN vs 直连对比是本项目现成的准自然实验（唯一差异是是否走
Anycast），比任何服务端调参都先做——它是免费的，且能直接把根因定位到链路侧还是本机侧。

## 2026-07-28 · Xray 26.x 源码核对调优（v1.2.8）

### L23 · `xray -test` 不校验字段名，不能用它证明参数存在

**失败机制**：本轮准备用 `xray -test` 逐个验证候选参数是否被 26.3.27 支持，写了
`"totallyFakeField":123` 作对照组，结果同样返回 `Configuration OK.`。Xray 的 JSON 解析器
不启用 `DisallowUnknownFields`，未知字段被静默丢弃。若不做这个对照，本轮会把一批不存在的
字段当成"已验证可用"写进项目——这正是网上大量"调优配置"的来源。

**规则**：判断某个配置项是否存在、默认值是多少、0 值什么语义，**只能读对应 tag 的源码**
（`infra/conf/` 看字段与 `Build()` 默认值，`transport/internet/<传输层>/` 看运行时语义）。
`xray -test` 只能证明 JSON 合法与结构可构建，不能证明字段有效。任何时候引入新字段，
必须同时给出源码文件名与行号。

### L24 · 「留空即用默认值」在 xmux 上是错的

**失败机制**：直觉上"不写 xmux 就用官方默认值"，但 `infra/conf/transport_internet.go:394`
是 `if c.Xmux == (XmuxConfig{})` —— 默认值**只在整个 xmux 结构为零值时**注入，且注入的
`maxConcurrency` 是 `1-1`（等于不复用）。而只要显式写了任意一个 xmux 子字段，其余子字段
就保持零值、走各自的 `GetNormalized*` 语义（多为"不限制"）。

**规则**："显式写部分字段"与"整体留空"在 Xray 里可能走**完全不同的两条默认值路径**。
删减配置前先确认该结构体的默认值注入条件是 per-field 还是 whole-struct。
## 2026-07-28 · v2.0.0 回归上游基线

### L25 · 「参数优化」要按**作用机制**分类，不能按文件位置一刀切

**失败机制**：用户要求「参数优化都不要做」。`templates/nginx.conf.tmpl` 里混着两类东西：
`worker_connections 65535` / `backlog=65535` / `access_log off` 是**吞吐旋钮**（收益未测量，
纯猜测），而 `grpc_read_timeout 1h` 与 `resolver ipv6=off` 是**正确性修复**——前者对应
L11 记录的「每 60 秒断一次」，后者对应纯 v4 机器 `Network is unreachable`。
按文件整体回退到上游会连正确性一起退掉，把两个已修好的 bug 重新引入，而且症状隐蔽
（不是连不上，是间歇断流 + 每次探测多一次超时）。

**规则**：执行「去掉优化」这类指令前，先把每一处改动归类为
「**如果不做会坏** / **如果不做只是慢一点**」两类，只回退后者，并在提交说明里显式写出
这个划分与理由——否则读起来像没执行指令。判据是：能指出一个具体的**故障现象**就是正确性。

### L26 · 「和上游一样」要用**渲染后逐字节 diff** 证明，不是逐行 review 模板

**失败机制**：本次涉及 5 条节点 URI（每条上千字符的 URL 编码）、6 处 xmux、一个 200 行的
mihomo 模板。靠肉眼比对模板必然漏。做法是写一个 harness，用 `awk` 从**两棵树的
`dist/*.sh` 产物**里抽出真实的生成代码段（L5：不手抄副本），灌同一套假 env 后渲染，
再对渲染结果做 diff——`xray-config.json` 直接断言 IDENTICAL，节点 URI 按 query 参数
逐项 diff。结果是机器给出「节点 4 唯一差异是 `alpn: h2→h3`」，这是 review 给不出的结论。

**规则**：凡是承诺「与 X 一致」的改动，验收标准必须是**渲染产物的 diff**，而不是源码
review。harness 要覆盖全部 profile（L18），且抽取真实产物代码而非重写等价逻辑（L5）。

## 2026-07-29 · v2.0.1 外部优化建议裁决

### L27 · 外部审查报告的**取值**和**机制**要分开验，采纳前者不等于采纳后者

**失败机制**：一份外部报告给了 7 条建议，其中 3 条的取值可取但理由站不住：
`tcp_notsent_lowat 16384` 是通行值，可它写的"高带宽场景吞吐损失 20-40%"方向错了——
调小 notsent_lowat 减少的是本地套接字排队，是**延迟**收益；拥塞窗口由 BBR 与
rmem/wmem 决定，与该项无关。`gzip on 浪费 CPU` 更是整条前提不成立：XHTTP 走
`grpc_pass`，响应 `content-type: application/grpc`，而 nginx 默认 `gzip_types` 只有
`text/html`，代理密文根本没进压缩路径。若照单全收，仓库里会留下一批"数值对、注释错"
的代码，下一个人按错误注释推理就会做出错误的连带改动。

**规则**：收到外部优化建议，对每一条分别回答两个问题——「这个**取值**该不该改」与
「它给的**机制**对不对」。取值采纳、机制重写是常见结果，注释里只写自己能证实的部分
（同 L23）。整条前提不成立的要显式驳回并写明反证，不能默默跳过。

### L28 · "一行改动"的建议要查它的**配套前提**

**失败机制**：报告称 `worker_connections 65535` 是"一行改动但收益最大"。但 v2.0.0 在
同一个 hunk 里把 `worker_rlimit_nofile` 一起回退了，而 `LimitNOFILE=1048576` 只在
`xh tuning on` 时写 systemd drop-in（`06-tuning-lib.sh:159`），默认安装根本没有。
只改 worker_connections 的结果是 nginx 报
`worker_connections exceed open file resource limit`，实际上限仍是 unit 默认值——
**改了等于没改，还多一条 error 日志**。

**规则**：任何"一行就能修好"的建议，先 `git log -S<关键词>` 查它当初是**和什么一起**
被加进来或退出去的。资源上限类参数（连接数/句柄/内存）几乎总是成对出现，单独调一侧
是无效改动。

## 2026-07-29 · nginx listen backlog 的裁决

### L29 · 已经有观测手段的问题，不要用推测代替读数

**失败机制**：真机 `ss -lnt` 显示 nginx 的 Send-Q 是 511 而 `somaxconn` 是 65535，
我据此把「backlog 偏小」列为待办，准备像 `worker_connections` 那样加回
`backlog=65535`。但 `perf-audit.sh` 第 2 节**早就在采集** `ListenOverflows` /
`ListenDrops`——accept 队列到底溢出过没有，是一个自开机累计的确定数字，不需要推测。
差点第二次推翻 v2.0.0 的决定，靠的却是「看着小」而不是读数。

更关键的是这两件事**机制不同，不能类比**：`worker_connections` 是**并发连接数**的
硬上限，XHTTP 长连接会直接累积着撞上去；`backlog` 是 accept 队列，只影响**建连速率**，
且只在 worker 来不及 accept 时才溢出。前者能指名故障现象（502），后者不能——
除非计数器非 0。

**规则**：给某个参数下「偏小」的结论前，先查仓库里是否已有能证伪它的观测项。
有就去读，读到 0 就是「当前负载下够用」，按 L25 归为吞吐旋钮、不改。
同时把**判读规则写进采集工具本身**（而不是留在对话里），下次同样的问题由工具自答。
两个参数「看起来都是并发相关」不构成一起调的理由，要各自指出作用机制。

## 2026-07-30 · 卸载留下的中间态卡死下次安装

### L30 · `stop` 之后要复核进程真的死了，再删它的文件

**失败机制**：`cmd_uninstall` 写的是
`systemctl stop xray nginx hysteria-server >/dev/null 2>&1 || true`——
`|| true` 把停止失败整个吞掉，随后单元文件和 `/usr/local/bin/xray` 照删不误。
Linux 上删除正在运行的二进制，**进程会从内存继续跑**，于是留下一个
「进程还活着、unit 和二进制都没了」的中间态。

下一次安装时，官方 `install-release.sh` 检测到 `pidof xray` 非空就去
`systemctl stop xray.service`，而单元已被删 → `Unit xray.service not loaded`
→ 脚本 `exit 1`。用户屏幕上只有官方脚本的报错，完全看不出问题出在**上一次卸载**，
两者之间隔着一次重装，因果链很难自己拼出来。

**规则**：凡是「停服务 → 删文件」的顺序，中间必须插一步 `pgrep` 复核；
没停掉就 `pkill` 再 `pkill -9`，并等它真的消失。
`|| true` 只能用在「失败了也确实无所谓」的地方，不能用在**后续步骤依赖它成功**的命令上——
这里删文件就依赖停止成功。卸载收尾还要 `systemctl reset-failed`，
否则被删的 unit 会以 not-found 状态挂在 systemd 里干扰下次判断。

### L31 · 修了卸载不等于修了问题——旧版本的卸载脚本已经在用户机器上

**失败机制**：L30 的修复只对**将来**用新版卸载的人有效。而制造中间态的那份旧
`xh` 已经装在机器上了，我们改不到它。用户下次从任何版本重装，仍会撞上同一个错。

**规则**：修「A 留下的脏状态导致 B 失败」这类问题时，**A 和 B 两侧都要改**：
A 侧不再产生脏状态，B 侧遇到脏状态能自己清理。只改 A 是把修复押在
「用户已经升级到新版 A」这个不成立的前提上。判据是问一句：
「这个修复要生效，用户得先做什么？」——答案里若包含「先用新版跑一次」，就漏了 B 侧。

## 2026-07-30 · v2.0.1 节点集收敛为 Reality + Hysteria2

### L32 · 「只要 X 不要 Y」时，先确认 Y 是不是 X 的子集

**失败机制**：需求是「direct 节点都不要，只需要 reality 和 hysteria2 节点」。
按字面理解 direct = 直连 IP，那么节点 1/2（`Vless-reality-vision`、
`Vless-xhttp-reality`）**既是 direct 又是 reality**——两句话直接矛盾，
照任一句执行都会删错东西。
去读 `extensions/common-nodes/03-client-config.sh:5-6` 才发现项目里
「-direct」是**节点名后缀**，只有 `Vless-xhttp-tls-h3-direct` 和
`Hysteria2-direct` 带它。于是两句话立刻自洽：删前者、留后者、主脚本只留 Reality。

**规则**：遇到「不要 A、只要 B」而 A 与 B 看起来相交时，不要挑一句执行，
也不要凭常识给 A 下定义——去代码里找 A 的**实际命名来源**。
本项目的教训是「direct」是字面后缀而不是链路属性描述。

### L33 · 关节点前，先查谁按名字派生它（不只是谁按名字找它）

**失败机制**：L10 记的是「删节点前 grep 出所有定位点」。这次进一步：
`extensions/dual-cdn/01-read-existing.sh:16` 用 `NODE_RE_CDN_BOTH` 读 CDN 节点来
**派生自己的配置**，关掉 CDN 节点后它会 error 退出；而 `common-nodes`（产 Hysteria2 的
那个）虽然也引用同一个 `NODE_RE_CDN_BOTH`，但自 v1.2.1 起是**可选**读取
（`CDN_LINE` 读不到不中断），`dual-ip` 同样是 `if [[ -n "$CDN_LINE" ]]`。
三个扩展引用同一个变量，硬依赖程度却完全不同——只看「有没有引用」会得出
「关了会挂三个扩展」的错误结论，进而不敢做这个改动。

**规则**：查依赖要区分**硬依赖**（读不到就 error）与**软依赖**（读不到走降级分支）。
判据是看引用点后面紧跟的是 `|| error` 还是 `if [[ -n ... ]]`。
只有硬依赖才需要在文案里告诉用户怎么恢复（本次给 dual-cdn 的报错加了
`FEATURE_CDN_NODES=true` 提示）。

### L34 · 用开关关掉节点时，配套的服务端配置也要一起跳过

**失败机制**：关掉 `Vless-xhttp-tls-h3-direct` 只改客户端输出是不够的——
`extensions/common-nodes/02-server-config.sh` 还会往 nginx 插
`listen <port> quic` 和 `location ${XHTTP_PATH}`。节点 2 直连 xray 的 TCP 443、
不经 nginx，所以那段配置**只服务这条 h3 节点**，留着就是一个没有任何客户端的
QUIC 监听——既是无谓的攻击面，也让后来的人看不懂它为谁而存在。
同理「共用端口」模式（hysteria2 给 h3 做 QUIC 前置）在节点关闭后完全失去意义，
还继续问用户选，是让人在一个无效选项上做决定。

**规则**：功能开关要覆盖**该功能的全部产物**——客户端节点、服务端监听、
相关的交互提问，逐一列出再逐一 gate。清理类操作（幂等删除旧块）保持无条件执行，
这样从「开启」降级到「关闭」时能把上次装的东西清掉，而不是留成孤儿。

**规则**：批量关闭/删除前，对**每一条**单独写一行留或删的理由。

## 2026-07-30 · v2rayN TUN 的两类故障

### L37 · 「能用但测不出来」要先分清测试路径与业务路径

**失败机制**：用户报 `Vless-xhttp-tls-UDP-cdn` 能开网页但测速显示 -1。
若把 -1 当成「节点不通」，会去查服务端配置——方向全错。
关键是 v2rayN 的两种测试**路径不同**：
- **Tcping** 从本机**直连** `server:port`，**不经过代理**。TUN 接管默认路由后，
  这个直连请求会被自家 TUN 捞走 → 回环 → 超时 → -1；而浏览器流量正常经代理出去，
  所以「能上网但 Tcping -1」是**同一个 TUN 自环问题的另一个观测面**。
- **真连接延迟** 经代理请求内置 URL，默认第一条是
  `https://www.google.com/generate_204`（`Global.cs` 的 `SpeedPingTestUrls`）。
  该 URL 从落地不可达、或 QUIC+XHTTP 冷启动超时，都会给 -1 而业务无恙。

**规则**：收到「功能正常但指标异常」时，先问「这个指标是怎么测出来的」——
测试流量与业务流量是否走同一条路径、同一个出口、同一套路由规则。
不同就先解释差异，不要把指标异常当功能故障去查。
另外 **对 alpn=h3 的节点用 Tcping 语义本身就是错的**（Tcping 做 TCP 握手，
节点跑在 UDP 上），这类指标即使有数字也不可信。

### L38 · 客户端已知缺陷要写进产物，不能只留在 README 的一行注记里

**失败机制**：README 早就有一行「V2rayN v7.19.5+ 在 TUN 模式下链路可能不稳定，
需启用旧版 TUN 保护选项（PR #9005）」。但我生成的
`client-config-v2rayn-tun.txt` 只讲了直连清单和 strict route，**漏了这一条**——
而它恰恰是「开 TUN 后全部节点都不通」最可能的原因（v7.19+ 改用 Shadowsocks 中继
+ 端口路由防回环，该机制在部分 Windows 上直接失效）。用户装完只看那份清单，
按清单配完仍然全不通，而答案在他不会去翻的 README 里。

**规则**：为某个场景专门生成一份「照着做」的产物时，要把该场景**全部**已知故障
按「先排除哪个」的顺序列进去，而不是只列自己这次想到的那一类。
判据是问：「用户只读这份文件，能不能走完排障？」读不完就是漏了。
并且要标明两类故障的**区分方法**（本次：全不通 → 看 TUN 保护机制；
个别节点不通 → 看直连规则），否则用户不知道该先动哪个。

## 2026-07-30 · v2.0.3 移植上游 add-quic.sh

### L39 · 「默认关掉，因为收益未测量」是自我实现的理由

**失败机制**：v2.0.1 关掉两条上下行分离节点，写的理由是「配置最复杂、收益未经测量」。
但默认不输出，用户就永远拿不到这两条节点，也就**永远不会有测量**——
这个理由把自己锁死了，等于用一句听起来严谨的话永久隐藏一个功能。
用户这次直接要求默认打开。

未测量 + 提供关闭开关，把测量机会交给用户，而不是替他决定不需要。

### L40 · 两个扩展往同一个文件插配置，标记名必须互不相同

**失败机制**：本次移植的 `quic-h3` 与已有的 `common-nodes` 都会往 nginx.conf 插

**规则**：多个组件写同一个配置文件时，每个组件的标记必须带自己的命名空间
（本次用 `# BEGIN quic-h3` 对 `# BEGIN quic xhttp`）。新增前先
`grep -ho '# BEGIN [a-z0-9 -]*'` 列出**全部**已有标记，确认无重名。
共享的只能是「删自己那段」的逻辑，绝不能共享标记本身。

### L41 · 移植上游代码时，00/04 这类通用模块直接引用而不是复制

**背景**：新扩展需要 `00-env-utils.sh`（颜色、rawurlencode、URI 解析、
find_client_files）与 `04-subscription-output.sh`（订阅重生成 + 自检），
两者与 common-nodes 完全相同。

**规则**：构建脚本的 MODULES 数组直接指向 common-nodes 的原文件，不在新目录下
复制一份。复制出来的副本当时一致、日后必然漂移，而且漂移不会有任何报错
（同 L5：测试里手抄的函数副本测不到漂移）。
代价是两个扩展耦合在同一份 00/04 上——这正是想要的：改一处两边同时生效。

## 2026-07-30 · 三条 h3 节点全不通

### L42 · 自检工具只查了「配置写没写」，没查「进程真的 bind 没有」

**失败机制**：`xh diag` 只检查 TCP 443 与 TCP 8003 两个监听，**完全没有 UDP 检查**。
于是 add-quic-h3 三条节点全不通时，diag 跑完显示「服务端侧未发现问题」——
它检查的项目里根本不包含这条链路依赖的任何东西。
更细一层：nginx.conf 里有 `listen <port> quic` 不等于进程真的 bind 了那个 UDP 端口
（L14 的同一类盲区：`nginx -t` 不 bind 端口）。两者要分开查。

**规则**：新增一条链路（本次是直连 UDP/QUIC）时，同步问「现有自检覆盖它吗」。
覆盖不到就补，否则自检输出「未发现问题」比没有自检更糟——它会让人把排查方向
引到别处。检查项要成对：**配置里写了什么** 与 **进程实际 bind 了什么**。

### L43 · 云厂商安全组在机器外面，本机自检永远查不到

**失败机制**：Oracle Cloud / AWS / GCP 的安全组是**虚拟机之外**的一层过滤。
本机 `ss` 显示 UDP 正常监听、`nft list ruleset` 也放行，包仍可能在到达网卡之前
就被云平台丢掉。而默认安全列表通常只有 TCP 22 + TCP 443——**加 TCP 规则时不会
自动带上 UDP**，于是「走 CDN 的节点正常（CF 回源走 TCP）、直连 UDP 的全挂」
这个症状会精确出现，且所有本机检查都显示健康。

**规则**：自检脚本对「本机查不到的外部因素」要**显式点名**，不能沉默。
本机全绿时更要提醒——全绿恰恰是这类故障的典型表现。
并给出可判别的对照实验（本次：Hysteria2 也是直连裸 IP 的 UDP，
它通不通能把「UDP 通路」与「nginx QUIC 层」二分开）。

### L44 · 推翻自己上一轮的假设要显式说出来

**失败机制**：移植 add-quic-h3 时我写过「docs/8 记录的『直连 h3 不通』针对的是
Reality-块设计，本扩展是 CDN-块设计，结论不一定适用」。用户实测三条全不通后，
按 L15 找共同点：三条失败节点的唯一共同点是**直连 VPS 裸 IP 的 UDP**，
而 nginx 插在哪个块与此无关——我上一轮的区分是**无关变量**，
docs/8 的旧结论恰恰适用。

**规则**：提出「这次和上次不同，旧结论可能不适用」这类假设时，要同时写下
「什么证据会推翻它」。拿到实测结果后主动回头核对，并在回复里明说假设被推翻，
而不是悄悄换个说法继续往下走（同 L9：谨慎措辞不能变成长期误导）。

### L45 · 调优评审的盲区：只查性能参数，不查韧性参数

**失败机制**：v2.0.3 之前的调优面全部集中在"快"上——BBR、缓冲区、TFO、
`tcp_slow_start_after_idle`、`notsent_lowat`。这些是**性能侧**。而代理机器在
CDN 回源 + XHTTP 长连接场景下的真实损耗还有一大部分在**韧性侧**：
对端死亡后僵尸 TCP 连接要按 `tcp_retries2` 的默认值（15 ≈ 15 分钟）才被内核
回收，连接表槽位与 fd 一直被占；出站 SYN 默认重试 6 次等 3 分钟才放弃。
「调优」不等于「把吞吐旋钮拧到最大」——资源释放的速度同样决定一台机器能
同时服务多少连接。

**规则**：评审网络调优时按两维对照检查，不能只审性能维：
- **性能维**：buffer / bbr / tfo / qdisc / 并发队列——本项目已覆盖。
- **韧性维**：retry 超时（`tcp_retries2`、`tcp_syn_retries`）、NAPI budget
  （`netdev_budget`，软中断收不完的信号在 `/proc/net/softnet_stat` 的
  `time_squeeze`）、协议防御（`tcp_rfc1337`）。
两维都过一遍再下"参数已是最优"的结论。追加参数时保持本项目惯例：
小内存档（<4G）不写、只写自己的 sysctl.d 文件、best-effort 试写。

## 2026-08-02 · v3.1.1 · 审计上一轮改动

### L46 · 「运行时生效」与「已持久化」是两件事，验证表必须分开测

**失败机制**：`ubuntu_vps_optimize.sh` 把 sysctl 落盘写在第二阶段末尾，而
第三阶段的 `tcp_fastopen`、第七阶段的 `vm.swappiness` / `vm.vfs_cache_pressure`
在其后才调用 `try()`。这三项 `sysctl -w` 成功、运行时确实生效，但**没有写进
`/etc/sysctl.d/`**，重启即丢失。

真正致命的是验证环节：第十二阶段的 Before/After 表读的是 `sysctl -n`（运行时值），
显示 `tcp_fastopen = 3`——**报告成功，重启回退**。假阳性比直接失败更坏，因为
它消耗掉了用户"我已经验证过了"的信任额度。TFO 恰好是用户点名要的目标。

**规则**：凡是「运行时应用 + 落盘持久化」两步的操作，
1. 落盘必须放在**所有**写调用之后（或每次写后增量落盘），改动顺序时要重查；
2. 验证不能只读运行时值，必须**另外断言落盘文件里有这一项**
   （本次已加：落盘后 `grep -q "^${k} " "$SYSCTL_CONF"` 自检关键项）；
3. 阶段式脚本里，「收集数组 → 末尾统一落盘」的模式最容易在插入新阶段时被破坏，
   注释里要写明这个约束。

### L47 · `bash -n` 不检查嵌入的 awk / sed 程序

**失败机制**：`awk -v f="$feat" '$1==f":/{print $2}'` 里 `":/{print $2}` 是一个
未闭合的字符串。`bash -n` 只解析 shell 语法，单引号内的内容对它是不透明字面量，
所以**全部检查通过**。运行时 awk 报 `unterminated string`、输出为空，
外层 `if [[ "$CUR" == off ]]` 永不成立——第五阶段的 GRO/GSO/TSO 启用逻辑成了死代码，
而脚本照常打印"网卡优化"章节，看不出任何异常。

**规则**：shell 里嵌入的 awk / sed / python 程序要**单独喂一行样例数据验证**，
不能只靠 `bash -n`。判据：这段程序的输出如果为空，外层逻辑会不会静默跳过？
会的话就必须实测。

### L48 · 「A 有而 B 没有」的字段差异，先查同仓库的同类对象再下结论

**失败机制**：新增 `Vless-xhttp-tls-H2-cdn` 时，以「`scMinPostsIntervalMs` 仅 h3 需要」
为由把它去掉了。两个反证同时存在且都在手边：上游的 `xhttp+TLS+H2`（同为 alpn=h2）
带这个字段；本仓库自己的 `split-cdnup-realitydown`（同为 alpn=h2）也带
`MIHOMO_SC_MIN_POSTS_BLOCK`。该参数约束的是 packet-up 模式下 POST 的最小间隔，
与 alpn 版本无关——理由是凭印象编的（同 L3）。

**规则**：给新对象裁剪字段前，先 `grep` 同仓库里**同类**对象（这里是"另一条 alpn=h2
的 CDN 节点"）是否带该字段。同仓库的既有实现是比记忆更硬的证据；
差异要么有据可依，要么就是 bug。

## 2026-08-04 · v4.0.0 · 节点集精简为 5 条纯 Xray 协议

### L49 · 「只用 X」的约束要先去核对 X 的能力清单，再谈取舍

**失败机制**：用户要求「仅仅 xray」同时又要 TUIC v5 + Hysteria2 obfs。凭印象，
这两个都是独立项目的协议，结论会是「都做不到，需要 sing-box」。实际查证后是
两个不同的答案：Xray **v26.3.27（2026-03）已原生支持 Hysteria2 inbound**，
连 Salamander obfs 都有（走 `finalmask.udp[]`）；而 TUIC 确实不在 inbound 列表里。

如果不查，要么错误地拒绝了本可实现的 Hysteria2，要么错误地承诺了做不到的 TUIC。
两个错误方向相反，但根因同一个：拿记忆当能力清单。

**规则**：遇到「只用某工具实现 A+B+C」的约束，第一步永远是去查该工具**当前版本**
的能力清单（官方 inbound/outbound 列表、release notes），逐项标注「支持 / 不支持 /
需要哪个版本」，再把冲突项摆给用户做取舍。快速发展的项目（Xray 一年发 20+ 个版本）
里，一年前的认知就已经不可靠。

### L50 · 新功能的版本下限不只看「何时加入」，还要看「何时修好」

**失败机制**：Hysteria2 inbound 在 v26.3.27 加入，很自然会把版本下限写成 26.3.27。
但 issue #6184 显示 v26.3.27~v26.5.9 上 `finalmask` 的 UDP listener **收到第一个
无效包就死亡**，内核缓冲区静默溢出，此后丢弃所有合法流量直到重启——公网 UDP 扫描
噪音使它必然被触发，且同时影响 Hysteria2 与 XHTTP/3。真正的下限是修复版 26.6.1。

写 26.3.27 的话，用户装上能跑通 `xray -test`、节点也能连上，然后在几小时或几天后
「莫名其妙全挂」，且重启就好——这是最难排查的一类故障。

**规则**：为新功能设版本下限时，除了查「哪个版本加入」，还要搜该功能的 open/closed
issue 找已知崩溃与修复版本，取两者的较大值。搜索词用「功能名 + bug/crash/panic」。
把理由写进代码注释和文档，否则下一个人会把它「优化」回加入版本。

### L51 · 跨模块复用函数前先确认它在目标模块可见

**失败机制**：在 `src/11-client-config.sh` 里调用 `rawurlencode` 拼节点 URI。
该函数只定义在 `extensions/*/00-env-utils.sh`，主安装脚本的 MODULES 列表里没有
任何一个定义它的文件。`bash -n` 通过，运行时才 `command not found`——而它在
heredoc/字符串拼接里，失败后变量为空、URI 静默变成非法值。

同一批改动里还踩了第二次：`--reloadcmd` 里用 `${XRAY_RESTART_CMD}`，而
`02-os-service.sh` 只定义了 `NGINX_*` 系列。这条更隐蔽——它写进 acme.sh 配置，
**将来由 cron 执行**，届时连 shell 函数都不存在，只能用完整系统命令。

**规则**：跨文件引用函数或变量前，先 `grep -rn '名字' <构建产物的 MODULES 范围>`
确认在目标构建单元里可见，不要假设「项目里有」就等于「这里能用」。
特别地，写进配置文件、cron、systemd unit 的命令字符串是**脱离当前 shell 上下文**
执行的，里面只能用绝对路径的完整命令。

### L52 · 新增节点要连输出层一起交付，否则等于没做

**失败机制**：v4.0.0 新增 Hysteria2-obfs 节点，服务端 `finalmask.salamander` 写对了、
客户端 URI 的 `obfs=salamander&obfs-password=` 也拼对了，验证脚本逐项断言全绿。
但**用户视角看不到任何混淆信息**：`14-final-output.sh` 的参数清单、`xh info`
都没有 HY2_PASSWORD / OBFS_PASSWORD / 端口，用户的反馈就是「没有加入混淆」。

更糟的是 `xh diag`：整段 UDP 检查围绕旧架构写死——查 nginx 的 `listen quic` 段、
查 `/etc/hysteria/config.yaml`。而新节点由 **Xray 自己 bind UDP**，这两处都不存在，
于是诊断工具对新增的两条 UDP 节点**完全失效**，注释还留着「本项目唯一的 UDP 节点
是经 CDN 的」这句已经过时的断言。

**规则**：交付一个新节点/新服务，改动清单至少覆盖四层，缺一层就是没交付完：
1. 服务端配置生成
2. 客户端配置与订阅
3. **参数输出**（安装完成的清单 + `xh info`）——用户核对与手工配置的唯一来源
4. **诊断工具**（`xh diag`）——新监听端口、新失败模式、以及**删掉已失效的旧检查**
第 3/4 层最容易漏，因为功能"能用"，验证脚本也全绿。
自检问法：装完这台机器的人，从哪里能看到这个新东西的参数？它不通时诊断命令会说什么？
